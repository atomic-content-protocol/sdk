# Linux Sandboxes

Daytona provides **Linux sandboxes** as the default sandbox for AI agents. A Linux sandbox is an isolated runtime environment you manage programmatically to run code. Each sandbox has a dedicated filesystem, network stack, and allocated vCPU, RAM, and disk. Agents and developers can install packages, run servers, compile code, and manage processes.

Linux sandboxes run as **containers** or as **Linux virtual machines (VMs)**. The snapshot sets the sandbox class, and both classes use the same SDKs, CLI, and API. Linux sandboxes start from a snapshot or a Docker image, keep their filesystem across stop and start, and are deleted when a timeout elapses or on request.

| **Term**                   | **Description**                                                                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Sandbox**                | An isolated Linux environment created on demand to run code.                                                                           |
| **Container**              | A sandbox that runs as a Linux container and shares the kernel of the host. The default sandbox class.                                 |
| **Linux VM**               | A sandbox that runs as a virtual machine with its own Linux kernel. The hardware enforces the boundary between sandboxes.              |
| **Sandbox class**          | The runtime of a Linux sandbox: container or Linux VM. The snapshot sets the class.                                                    |
| **Image**                  | A packaged filesystem that defines the software a sandbox starts with. Container sandboxes can start from a Docker image.              |
| **Snapshot**               | A pre-configured template that new sandboxes start from.                                                                               |
| **Toolbox**                | The Daytona daemon inside the sandbox that serves file, Git, and process requests.                                                     |

## Use cases

Linux sandboxes are used wherever code must run in a real environment, but you cannot trust the code or you cannot afford for it to affect anything else.

- **Code execution for AI agents**: an agent writes code, runs it in a sandbox, reads the output, and decides what to do next. The sandbox gives the agent a real shell and filesystem while keeping its actions away from your infrastructure.
- **Coding agents**: an agent clones a repository, installs dependencies, edits files, runs the test suite, and pushes a branch, all inside one sandbox.
- **Reinforcement learning (RL) and evaluation**: each episode or test case gets a clean, identical machine created from a shared snapshot, so results do not depend on leftover state and each environment stays cheap.
- **Untrusted user code**: online coding platforms, grading systems, code interpreters, and plugin hosts run code submitted by users or generated by a model without exposing other users or the service.
- **Computer-use agents**: an agent operates a graphical desktop, a browser, or desktop applications through screenshots and input events.
- **Development environments**: a developer gets a preconfigured machine from an image, connects over SSH or from an editor, and previews web applications through a URL.
- **Long-lived and branching agent sessions**: a Linux VM sandbox pauses when the agent goes idle and resumes with its processes and memory intact, and is forked to try several approaches from the same point.

Create a sandbox.


Create a container sandbox. A sandbox created without a snapshot uses the Daytona default snapshot. To pick a size, set one of the default container snapshots.

Create a Linux sandbox from your own snapshot. Create the snapshot from any publicly accessible image, then create sandboxes from it.

1. Go to [Daytona Snapshots ↗](https://app.daytona.io/dashboard/snapshots)
2. Click <Button>Create Snapshot</Button>
3. Enter the <Button>Snapshot Name</Button>, for example **`my-snapshot`**
4. Enter the <Button>Image</Button>, for example **`python:3.12`**
5. Click <Button>Create</Button>
6. Go to [Daytona Sandboxes ↗](https://app.daytona.io/dashboard/sandboxes)
7. Click <Button>Create Sandbox</Button>
8. Select the <Button>Snapshot</Button> **`my-snapshot`**
9. Click <Button>Create</Button>


```python
from daytona import CreateSandboxFromSnapshotParams, CreateSnapshotParams, Daytona

daytona = Daytona()

# Create a snapshot from an image
daytona.snapshot.create(
    CreateSnapshotParams(
        name="my-snapshot",
        image="python:3.12",
    ),
)

# Create a sandbox from the snapshot
sandbox = daytona.create(CreateSandboxFromSnapshotParams(snapshot="my-snapshot"))
```

## Nested virtualization

Daytona provides nested virtualization for Linux VM sandboxes. Nested virtualization exposes KVM (`/dev/kvm`) inside the guest, so the sandbox can run its own virtual machines with hardware acceleration.

:::note
KVM sandboxes must be enabled for your organization. Contact [support@daytona.io](mailto:support@daytona.io).
:::

## Filesystem snapshot

A filesystem snapshot, also called a cold snapshot, saves the filesystem of a stopped Linux sandbox. Both sandbox classes support filesystem snapshots. A snapshot without the include memory option is a filesystem snapshot.



```python
from daytona import Daytona, CreateSandboxFromSnapshotParams

daytona = Daytona()
sandbox = daytona.create()

# Write a file to the filesystem
sandbox.fs.upload_file(b"done", "setup.log")

# A filesystem snapshot requires a stopped sandbox
sandbox.stop()
sandbox.create_snapshot("my-snapshot")

# A sandbox created from the snapshot starts with the same filesystem
new_sandbox = daytona.create(CreateSandboxFromSnapshotParams(snapshot="my-snapshot"))
content = new_sandbox.fs.download_file("setup.log")
print(content.decode())  # done
```


```typescript
import { Daytona } from '@daytona/sdk'

const daytona = new Daytona()
const sandbox = await daytona.create()

// Write a file to the filesystem
await sandbox.fs.uploadFile(Buffer.from('done'), 'setup.log')

// A filesystem snapshot requires a stopped sandbox
await sandbox.stop()
await sandbox.createSnapshot('my-snapshot')

// A sandbox created from the snapshot starts with the same filesystem
const newSandbox = await daytona.create({ snapshot: 'my-snapshot' })
const content = await newSandbox.fs.downloadFile('setup.log')
console.log(content.toString()) // done
```


```ruby
require 'daytona'

daytona = Daytona::Daytona.new
sandbox = daytona.create

sandbox.stop
sandbox.create_snapshot(name: 'my-snapshot')

# A sandbox created from the snapshot starts with the same filesystem
new_sandbox = daytona.create(Daytona::CreateSandboxFromSnapshotParams.new(snapshot: 'my-snapshot'))

puts content # done
```


```go
package main

import (
	"context"
	"fmt"

	"github.com/daytona/clients/sdk-go/pkg/daytona"
	"github.com/daytona/clients/sdk-go/pkg/types"
)

func main() {
	client, _ := daytona.NewClient()
	ctx := context.Background()
	sandbox, err := client.Create(ctx, types.SnapshotParams{})
	if err != nil {
		panic(err)
	}

	// Write a file to the filesystem
	if err := sandbox.FileSystem.UploadFile(ctx, []byte("done"), "setup.log"); err != nil {
		panic(err)
	}

	// A filesystem snapshot requires a stopped sandbox
	if err := sandbox.Stop(ctx); err != nil {
		panic(err)
	}
	if err := sandbox.CreateSnapshot(ctx, "my-snapshot"); err != nil {
		panic(err)
	}

	// A sandbox created from the snapshot starts with the same filesystem
	newSandbox, err := client.Create(ctx, types.SnapshotParams{Snapshot: "my-snapshot"})
	if err != nil {
		panic(err)
	}
	content, err := newSandbox.FileSystem.DownloadFile(ctx, "setup.log", nil)
	if err != nil {
		panic(err)
	}
	fmt.Println(string(content)) // done
}
```


```java
import io.daytona.sdk.Daytona;
import io.daytona.sdk.Sandbox;
import io.daytona.sdk.model.CreateSandboxFromSnapshotParams;

public class App {
    public static void main(String[] args) {
        try (Daytona daytona = new Daytona()) {
            Sandbox sandbox = daytona.create();

            // Write a file to the filesystem
            sandbox.fs.uploadFile("done".getBytes(), "setup.log");

            // A filesystem snapshot requires a stopped sandbox
            sandbox.stop();
            sandbox.createSnapshot("my-snapshot");

            // A sandbox created from the snapshot starts with the same filesystem
            CreateSandboxFromSnapshotParams fromSnapshot = new CreateSandboxFromSnapshotParams();
            fromSnapshot.setSnapshot("my-snapshot");
            Sandbox newSandbox = daytona.create(fromSnapshot);
            byte[] content = newSandbox.fs.downloadFile("setup.log");
            System.out.println(new String(content)); // done
        }
    }
}
```

## Filesystem persistence

Filesystem persistence keeps the contents of a sandbox's disk: files, installed packages, cloned repositories, and build artifacts. A sandbox with a preserved filesystem starts with its environment intact, with nothing to reinstall or rebuild.

Linux sandboxes preserve their filesystem across [stop and start](#stop--start), [archive](https://www.daytona.io/docs/en/sandboxes.md#archive-sandboxes), and [filesystem snapshots](#filesystem-snapshot) created from a sandbox. An [ephemeral sandbox](https://www.daytona.io/docs/en/sandboxes.md#ephemeral-sandboxes) is deleted on stop, so its filesystem is not kept. The sandbox classes differ in where the preserved filesystem is stored.

| **Sandbox class** | **Filesystem persistence**                                                                                                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Container**     | Filesystem is preserved through stop and start: it stays on the runner and counts against disk quota while stopped. Archive moves it to object storage and frees the quota, and starting an archived sandbox restores it. Use filesystem snapshots to capture the filesystem. |
| **Linux VM**      | Filesystem is preserved through stop and start: stopping offloads it to nearby storage and releases disk quota, starting restores it. Archive is not needed. Use filesystem snapshots to capture the filesystem.                                 |

## Memory persistence

Memory persistence keeps the runtime state of a sandbox: running processes, open connections, and everything loaded in RAM. A sandbox with preserved memory continues from the point it was frozen, with processes still running, instead of starting from a clean boot.

Linux VM sandboxes preserve their memory across [pause and resume](#pause--resume), [memory snapshots](#memory-snapshot) created from a sandbox, and [forks](#fork). Memory state is cleared on every stop. The sandbox classes differ in whether memory can be preserved without keeping the sandbox running:

| **Sandbox class** | **Memory persistence**                                                                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Container**     | Memory persists only while the sandbox is running. Set the auto-stop interval to zero to run indefinitely, or relaunch processes after each start. Pause is not supported.                                   |
| **Linux VM**      | Memory is preserved through pause and resume: pausing freezes the VM with memory intact, resuming continues all processes from the point they were frozen. Use memory snapshots or forks to capture memory. |


```python
from daytona import Daytona, CreateSandboxFromSnapshotParams, SessionExecuteRequest

daytona = Daytona()
sandbox = daytona.create(CreateSandboxFromSnapshotParams(snapshot="daytona-vm-small"))

# Start a process that runs in the background
sandbox.process.create_session("keepalive")
response = sandbox.process.execute_session_command(
    "keepalive",
    SessionExecuteRequest(command="sleep 3600", run_async=True),
)

# Pause keeps the filesystem and memory
sandbox.pause()

# Start resumes every process from the point where the sandbox paused
sandbox.start()
command = sandbox.process.get_session_command("keepalive", response.cmd_id)
print(command.exit_code)  # None: the process is still running
```

## Lifecycle

Every Linux sandbox moves through a lifecycle. A Linux sandbox can have several different states. Each state reflects the status of your sandbox. A Linux sandbox transitions between states in response to user actions, or automatically when one of its [timeouts](#timeouts) elapses.

| **Stop and start**                | ✓             | ✗                         | ✓            | ✗                        |
| **Pause and resume**            | ✗             | ✗                         | ✓            | ✗                        |
| **Fork**                                 | ✗             | ✗                         | ✓            | ✓                        |
| **Archive** | ✓           | ✗                         | ✗            | ✗                        |
| **Delete**                             | ✓             | ✓                         | ✓            | ✓                        |
| **Filesystem persistence** | ✓         | ✗                         | ✓            | ✗                        |
| **Memory persistence**     | ✗             | ✗                         | ✓            | ✗                        |
| **Memory snapshot**           | ✗             | ✗                         | ✓            | ✓                        |
| **Filesystem snapshot**   | ✓             | ✗                         | ✓            | ✗                        |
| **Nested virtualization** | ✗           | ✗                         | ✓            | ✓                        |
| **Desktop**                                       | ✓ VNC         | ✓ VNC                     | ✓ VNC        | ✓ VNC                    |

| **Stopped**       | **Archiving**    | An archive is requested on a container sandbox, or the auto-archive interval elapses. |
| **Archived**      | **Restoring**    | A start is requested on an archived container sandbox.                               |
| **Started**       | **Snapshotting** | A memory snapshot is requested on a Linux VM sandbox.                                |
| **Stopped**       | **Snapshotting** | A filesystem snapshot is requested.                                                  |
| **Started**       | **Forking**      | A fork is requested on a Linux VM sandbox.                                           |
| **Started**       | **Deleting**     | A delete is requested, or an ephemeral sandbox is stopped.                           |
| **Stopped**       | **Deleting**     | A delete is requested, or the auto-delete interval elapses.                          |
| **Deleting**      | **Deleted**      | The sandbox is removed and its resources are released.                               |

</Collapsible>

### Fork

Fork a sandbox.


Forking is not supported for container sandboxes. Use [create snapshot from sandbox](https://www.daytona.io/docs/en/snapshots.md#create-snapshot-from-sandbox) to capture filesystem state, then create a new sandbox from that snapshot.


Forking creates a duplicate of a Linux VM sandbox's filesystem and memory state in a new sandbox. The forked sandbox is fully independent: it can be started, stopped, and deleted without affecting the original.

Daytona tracks the parent-child relationship in a fork tree, so you can trace a fork's lineage back to the sandbox it was created from. You can fork a fork to build branches. The parent sandbox cannot be deleted while it has active fork children.

A fork of a [KVM sandbox](#nested-virtualization) inherits the `kvm` setting. Forking a KVM sandbox returns a `403` error if KVM sandboxes are not enabled for your organization.

1. Go to [Daytona Sandboxes ↗](https://app.daytona.io/dashboard/sandboxes)
2. Click the three-dot menu (**⋮**) next to the started Linux VM sandbox you want to fork
3. Select <Button>Fork</Button>

### Timeouts

Daytona stops, pauses, archives, or deletes a sandbox when a timeout elapses. Each timeout is set in minutes. Zero disables auto-stop, auto-pause, and wall-clock TTL. Zero does not disable auto-archive or auto-delete: auto-archive set to zero uses the maximum interval of 30 days, and auto-delete set to zero deletes the sandbox as soon as it stops. To disable auto-delete, set it to -1.

| **Interval**                                                   | **Container**                | **Linux VM**                        | **Action**                                         |
| -------------------------------------------------------------- | ---------------------------- | ----------------------------------- | -------------------------------------------------- |
| **Auto-stop**             | ✓ (default 15 minutes)       | ✓                                   | Stops the sandbox after inactivity.                |
| **Auto-pause**                                      | ✗                            | ✓ (default 60 minutes)              | Pauses the sandbox after inactivity.               |
| **Auto-archive**       | ✓                            | ✗                                   | Archives a stopped sandbox.                        |
| **Auto-delete**         | ✓                            | ✓                                   | Deletes a stopped sandbox.                         |
| **Wall-clock TTL**                              | ✓                            | ✓                                   | Deletes the sandbox at a fixed deadline, in any state. |

#### Auto-pause

The auto-pause interval sets the amount of time after which an idle VM sandbox is automatically [paused](#pause--resume). Auto-pause applies only to [VM sandboxes](https://www.daytona.io/docs/en/sandboxes.md#vm-sandboxes) and is mutually exclusive with the [auto-stop interval](https://www.daytona.io/docs/en/sandboxes.md#auto-stop-interval): at most one of the two intervals may be non-zero. Ephemeral sandboxes cannot have auto-pause enabled.

The interval is set in minutes:

- **`0`**: disables the auto-pause functionality
- if neither auto-pause nor auto-stop is set, non-ephemeral sandbox classes that support pausing default to an auto-pause interval of 60 minutes with auto-stop disabled

The sandbox pauses after no new events occur for the specified interval. Events include sandbox state changes and interactions with the sandbox through the SDK. Interactions through [sandbox previews](https://www.daytona.io/docs/en/preview.md) do not reset the timer.


Auto-pause is not supported for container sandboxes. Use [auto-stop](https://www.daytona.io/docs/en/sandboxes.md#auto-stop-interval) to stop a container sandbox after a period of inactivity.


1. Go to [Daytona Sandboxes ↗](https://app.daytona.io/dashboard/sandboxes)
2. Click <Button>Create Sandbox</Button>
3. Select a Linux VM snapshot
4. Set **`auto-pause`** interval to the desired value in minutes
    - **`0`**: disables the auto-pause functionality
    - if neither auto-pause nor auto-stop is set, the default interval of 60 minutes is used with auto-stop disabled
5. Click <Button>Create</Button>


```python
from daytona import CreateSandboxFromSnapshotParams

sandbox = daytona.create(CreateSandboxFromSnapshotParams(
    snapshot="daytona-vm-small",
    # Auto-pause after 1 hour of inactivity
    auto_pause_interval=60,
))

# Update the auto-pause interval on an existing sandbox
sandbox.set_auto_pause_interval(60)

# Disable auto-pause
sandbox.set_auto_pause_interval(0)
```

#### Wall-clock TTL

The wall-clock TTL (time-to-live) sets a hard upper bound on how long a sandbox may exist. Unlike the [auto-delete interval](https://www.daytona.io/docs/en/sandboxes.md#auto-delete-interval), which counts time only while the sandbox is stopped, TTL runs as wall-clock time from creation (or from the moment you last set it) and destroys the sandbox in any state: started, stopped, paused, or archived.

Set `ttl_minutes` when creating a sandbox, or update it later. The value is in minutes:

- **`0`**: disables the TTL
- if not set, the sandbox has no TTL deadline

Calling `set_ttl` after creation resets the deadline from the current moment. Use wall-clock TTL for agent sessions, CI jobs, and any sandbox that must not outlive a fixed deadline.


```python
sandbox = daytona.create(CreateSandboxFromSnapshotParams(
    snapshot="daytona-vm-small",
    ttl_minutes=120,
))

# Reset the deadline to 60 minutes from now
sandbox.set_ttl(60)
```
